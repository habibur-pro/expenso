# Spec: Homepage Design

## Overview

Replace the default `create-next-app` starter page with Expenso's public marketing homepage: the first real surface of the product and the entry point that funnels visitors into sign-up and login. This is step 01 of the roadmap, so no database, authentication, or expense data exists yet — the homepage is a fully static, server-rendered marketing page that explains what Expenso does (track expenses, organize by category, view history and spending analytics) and links to the future auth routes. It also establishes the public-facing SEO baseline (real metadata, `robots.ts`, `sitemap.ts`, OG/Twitter images) and the shared visual language (spacing scale, section rhythm, typography, existing shadcn tokens) that later public pages will reuse.

## Depends on

Nothing. This is the first feature step. The project currently contains only the Next.js starter (`src/app/layout.tsx`, `src/app/page.tsx`, `src/app/globals.css`), one shadcn component (`src/components/ui/button.tsx`), and `src/lib/utils.ts`. There is no `prisma/` directory, no auth, no services, and no API routes.

## User flow

**Entry point:** A visitor lands on `/` from a search result, a shared link, or by typing the domain.

**Above the fold:** A sticky site header shows the Expenso wordmark, in-page navigation anchors (Features, How it works, FAQ), a "Log in" text link, and a primary "Get started" button. Immediately below, the hero states the value proposition in a single `<h1>`, a one-line subheading, a primary CTA ("Get started free") and a secondary CTA ("See how it works", an in-page anchor to the How it works section).

**Scrolling:** The visitor scrolls through a static product preview (a non-interactive mock of the expense dashboard built from plain markup — no charting library, no live data), a feature grid, a three-step "How it works" section, an FAQ, and a closing CTA band, ending at the site footer.

**User actions:**

- Click "Get started" / "Get started free" / the closing CTA → navigate to `/register`.
- Click "Log in" → navigate to `/login`.
- Click a nav anchor or "See how it works" → in-page scroll to that section.
- On mobile, tap the menu button → the mobile nav panel opens with the same links; tapping a link closes it and scrolls to the target.
- Expand/collapse an FAQ item.

**Form interactions:** None. The homepage contains no forms, no email capture, and no user input.

**Validation behavior:** Not applicable — there is no user input on this page.

**Loading behavior:** The page is fully static (prerendered at build time). There are no data fetches, so there are no skeletons or spinners. Fonts load via `next/font` with the existing self-hosted Geist setup; the OG image is generated at build time and never blocks the page.

**Success behavior:** The page renders completely on first paint with no layout shift, and every CTA reaches its destination.

**Error behavior:** No runtime error states exist on the page itself. `/register` and `/login` do not exist yet, so those links will 404 until the auth step lands — this is expected and intentional at step 01; do not create stub auth pages as part of this spec.

**Empty states:** Not applicable — all content is static copy.

**Confirmation behavior:** Not applicable — no destructive or persisted actions.

**Navigation behavior:** All internal navigation uses `next/link`. In-page anchors use `href="#section-id"` against `id` attributes on the corresponding `<section>` elements. Anchor scrolling relies on CSS `scroll-behavior` / `scroll-margin-top` so sticky-header overlap is avoided — no JavaScript scroll handlers.

## API Routes

No API route changes.

The homepage is a static Server Component with no data requirements. `src/app/robots.ts` and `src/app/sitemap.ts` are Next.js metadata file conventions (special cached Route Handlers generated by the framework) — they are public by definition, expose no user data, and are not custom Route Handlers under `src/app/api/`.

## Database changes

No database changes.

There is no `prisma/` directory or `prisma/schema.prisma` in the repository yet, and the homepage requires none. Do not create a Prisma schema, do not add a Prisma client, and do not touch the `DB_URI` environment variable as part of this step.

## components & ui

All homepage sections live in a single new folder, `src/components/marketing/` (public-facing surfaces only). Do not create `expenses/`, `analytics/`, or `dashboard/` folders in this step.

**Create:**

- `src/components/marketing/section.tsx` — small shared layout primitive (max-width container, consistent vertical padding, optional `id`) so every section shares one rhythm. Keep it minimal; do not build a layout abstraction beyond this.
- `src/components/marketing/site-header.tsx` — Server Component. Sticky top bar: wordmark (lucide icon + "Expenso" text, wrapped in a `next/link` to `/`), desktop nav anchors, "Log in" link, "Get started" button. Renders `<MobileNav />` for the small-screen menu. Uses `<header>` + `<nav aria-label="Main">`.
- `src/components/marketing/mobile-nav.tsx` — the only `"use client"` component in this feature. A disclosure button (lucide `Menu` / `X`) toggling a mobile panel with the same links. Requires `aria-expanded`, `aria-controls`, an accessible label, `Escape` to close, and closing on link click. Hidden at `md:` and above.
- `src/components/marketing/hero.tsx` — Server Component. The page's single `<h1>`, subheading, primary + secondary CTAs, rendering `<HeroPreview />`.
- `src/components/marketing/hero-preview.tsx` — Server Component. Static, non-interactive mock of the expense dashboard (summary stat tiles, a few sample expense rows, a simple CSS bar breakdown). Built from plain markup and Tailwind tokens — **no charting library, no images, no live data**. Marked `aria-hidden="true"` (decorative) so screen readers skip the sample numbers.
- `src/components/marketing/feature-grid.tsx` — Server Component. `<section id="features">` with six feature cards (fast expense entry, categories, search and filter, spending analytics, trends over time, works on every device), each with a lucide icon, `<h3>`, and short copy.
- `src/components/marketing/how-it-works.tsx` — Server Component. `<section id="how-it-works">` with three numbered steps: create an account, add expenses, see where your money goes.
- `src/components/marketing/faq.tsx` — Server Component. `<section id="faq">` with four to six questions. Implemented with native `<details>` / `<summary>` so it is keyboard-accessible and needs zero client JS; do not pull in a shadcn accordion for this.
- `src/components/marketing/cta-section.tsx` — Server Component. Closing conversion band repeating the primary CTA to `/register`.
- `src/components/marketing/site-footer.tsx` — Server Component. `<footer>` with wordmark, one-line blurb, a small link column, and copyright.

**Modify:**

- `src/app/page.tsx` — replace the entire starter content with the homepage: compose `SiteHeader`, `Hero`, `FeatureGrid`, `HowItWorks`, `Faq`, `CtaSection`, `SiteFooter`. Remove the `next/image` starter markup and all Vercel/Next.js template links. Wrap the sections in `<main>`; header and footer sit outside `<main>`. Export page-level `metadata` (title, description, `openGraph`, `twitter`, `alternates.canonical: "/"`). Stays a Server Component with no `"use client"`.
- `src/app/layout.tsx` — replace the `"Create Next App"` / `"Generated by create next app"` metadata with real Expenso root metadata: `metadataBase` from the site URL env var, `title` as `{ default, template }`, description, `openGraph`, `twitter`. Also fix the font wiring: `globals.css` maps `--font-sans: var(--font-sans)` but `layout.tsx` declares Geist as `--font-geist-sans`, so the `font-sans` utility resolves to nothing today — change the Geist variable to `--font-sans` (leave `Geist_Mono` / `--font-geist-mono` as is). Do not otherwise restructure the layout.
- `src/app/globals.css` — additive only: add `scroll-behavior: smooth` (respecting `prefers-reduced-motion`) and a `scroll-margin-top` default for anchor targets inside the existing `@layer base` block. Do not change the existing color tokens, radius scale, or `@theme inline` mappings.

**Pages / routes affected:**

- `src/app/page.tsx` — the homepage itself.
- `src/app/layout.tsx` — root metadata and font variable.
- `src/app/robots.ts` (new) — allow `/`; disallow `/api/`, `/dashboard`, `/expenses`, `/analytics`; reference the sitemap.
- `src/app/sitemap.ts` (new) — `/` only, since it is the sole public indexable route at this step.
- `src/app/opengraph-image.tsx` (new) and `src/app/twitter-image.tsx` (new) — build-time social images via `ImageResponse` from `next/og` (built into Next 16, not a new package). `twitter-image.tsx` may re-export the default, `size`, `alt`, and `contentType` from `opengraph-image.tsx` rather than duplicating the markup.

**Responsive requirements:**

- **Mobile (< 640px):** single column everywhere; hamburger menu; CTAs full-width and stacked; hero preview scales down or clips gracefully without horizontal page scroll; type scale steps down.
- **Tablet (640–1024px):** two-column feature grid; nav still collapsed below `md`; hero remains stacked or side-by-side depending on space.
- **Desktop (>= 1024px):** full horizontal nav, three-column feature grid, side-by-side or centered hero with the preview at full size, capped content width.
- The page body must never scroll horizontally at any width.

**Loading / empty / error states:** No async content, so none apply. Do not add skeletons for static copy.

**Accessibility:**

- Exactly one `<h1>` (in the hero); sections use `<h2>`, cards use `<h3>` — no level skipping.
- Semantic landmarks: `<header>`, `<nav aria-label="Main">`, `<main>`, `<section>` with `aria-labelledby` pointing at its heading, `<footer>`.
- All interactive elements reachable and operable by keyboard, with visible focus rings (the existing `focus-visible:ring` treatment in `button.tsx`).
- The mobile menu button has an accessible name, `aria-expanded`, and `aria-controls`.
- Decorative lucide icons get `aria-hidden="true"`; the decorative hero preview is hidden from assistive tech.
- Text meets WCAG AA contrast in both light and dark token sets.
- Motion respects `prefers-reduced-motion`.

**Design constraints:** Use only Tailwind CSS v4 utilities and the existing token set in `globals.css` (`bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, `bg-card`, `bg-primary`, the `--radius-*` scale). Reuse the existing `Button` component (`variant="default"` for primary CTAs, `variant="outline"` or `"ghost"` for secondary; `size="lg"` where appropriate) rather than hand-rolling button styles. Dark mode is driven by the existing `.dark` class tokens — **do not add a theme toggle or `next-themes` in this step** (nothing sets the `.dark` class yet, and adding it is out of scope). Do not introduce a second design system, a CSS file per component, or inline styles.

## Services & Business Logic

No service changes.

The homepage has no business logic and no database access. Static marketing copy (feature list, steps, FAQ entries) may be declared as typed `const` arrays colocated in the component that renders them, or in `src/lib/constants/` if shared by more than one component — do not create a service for static content.

## Validation

No validation required.

The homepage accepts no user input: no forms, no query parameters, no route parameters, no request bodies, no filters, no sort parameters, no IDs, no amounts, no dates. Do not add Zod schemas for this feature. Zod validation begins with the first feature that accepts user input (authentication).

## Authorization & Data Ownership

Not applicable to this feature — the homepage is a fully public page that reads no user-owned data.

Rules that still bind this step:

- The homepage must not attempt to read a session, call Prisma, or render user-specific content. It renders identically for every visitor and stays statically prerenderable.
- The header shows "Log in" / "Get started" unconditionally. Do not add conditional auth-aware rendering, and never derive auth state from client storage, cookies read on the client, or a client-provided `userId`.
- `src/app/robots.ts` must disallow crawling of the future authenticated areas (`/dashboard`, `/expenses`, `/analytics`) and `/api/`. `robots.txt` is a crawler hint only, never an access control mechanism — real server-side authorization arrives with the auth step and is not substituted by this file.
- `src/app/sitemap.ts` must list only public, indexable routes — never authenticated routes.

## Rules for implementation

- Follow `CLAUDE.md` and `AGENTS.md`. `AGENTS.md` warns that this Next.js version differs from training data — consult `node_modules/next/dist/docs/` (Metadata API, `robots.ts`, `sitemap.ts`, `opengraph-image`) before writing code, and use Context7 for anything version-sensitive or unfamiliar.
- Make the smallest clean change that fully solves the requested task.
- Do not implement features outside the requested scope (no auth pages, no dashboard, no Prisma schema, no theme toggle, no analytics).
- Do not refactor unrelated code.
- Do not remove existing functionality without explicit permission. Leave the unused starter SVGs in `public/` alone.
- Follow existing project conventions: `PascalCase` components, `camelCase` variables and functions, kebab-case filenames, `@/` path aliases, `const` over `let`, no `any`, prefer type inference.
- Prefer Server Components. `"use client"` is permitted in exactly one file: `src/components/marketing/mobile-nav.tsx`.
- Never access Prisma directly from Client Components (and do not access Prisma at all in this step).
- Keep business logic out of UI components; put reusable business logic in services.
- Use Next.js Route Handlers for backend logic (none required here).
- Validate all server-side user input with Zod (no user input in this feature).
- Never trust client-provided `userId`; enforce authentication and authorization server-side; verify ownership of user-owned resources (not applicable here, but the homepage must not fake auth-aware UI).
- Use MongoDB through Prisma; avoid raw MongoDB queries; use a shared Prisma client instance (no DB access in this step).
- Avoid floating-point arithmetic for exact monetary values, and do not silently mix currencies — the sample numbers in the hero preview are hardcoded display strings, not computed values.
- Never fetch unbounded expense lists; paginate potentially large lists; prefer server-side or database-side aggregation; do not ship unnecessary raw data to the client.
- Return safe client-facing errors; never expose Prisma, database, or internal errors to users.
- Keep secrets server-side. Never hardcode credentials, keys, tokens, or secrets. `NEXT_PUBLIC_SITE_URL` is a public origin and is the only `NEXT_PUBLIC_`-prefixed variable this feature may add; never prefix a private variable with `NEXT_PUBLIC_`.
- Use Tailwind CSS for styling; reuse the existing `Button` and the token set in `globals.css`; avoid inline styles.
- Keep all UI responsive across mobile, tablet, and desktop; maintain accessibility (heading order, landmarks, focus states, ARIA on the mobile menu, reduced motion).
- Avoid unnecessary client-side state and `useEffect` — the only client state permitted is the mobile menu's open/closed boolean.
- Avoid unnecessary database queries and API requests (this page should make zero).
- Do not add dependencies unless necessary; check installed package versions before using APIs.
- Do not make destructive database changes without explicit permission.
- Do not modify configuration unless required (`next.config.ts`, `eslint.config.mjs`, `tsconfig.json`, `components.json`, and `postcss.config.mjs` should all remain untouched).
- Do not modify unrelated files.

## Definition of done

Verified by running `pnpm dev` and `pnpm build`:

1. `pnpm lint` passes with no new errors or warnings.
2. `pnpm build` succeeds and reports `/` as a static (prerendered) route.
3. Visiting `/` shows the Expenso homepage — no `create-next-app` copy, no Next.js or Vercel logos, and no links to nextjs.org or vercel.com anywhere in the page source.
4. The page renders header, hero with static preview, feature grid, how-it-works, FAQ, closing CTA, and footer, in that order.
5. Page source contains exactly one `<h1>`, and heading levels descend without skipping (`h1` → `h2` → `h3`).
6. Viewing source on `/` shows a real Expenso `<title>` and `<meta name="description">` (not "Create Next App"), plus `og:title`, `og:description`, `og:image`, `twitter:card`, `twitter:image`, and `<link rel="canonical">`.
7. `/opengraph-image` and `/twitter-image` each return an image with HTTP 200.
8. `/robots.txt` returns `Allow: /`, disallows `/api/`, `/dashboard`, `/expenses`, and `/analytics`, and includes the `Sitemap:` line.
9. `/sitemap.xml` returns valid XML listing `/` and no authenticated routes.
10. At 375px, 768px, and 1440px widths the layout is correct and `document.documentElement.scrollWidth` never exceeds the viewport width (no horizontal scroll).
11. At 375px the hamburger opens the mobile menu, `aria-expanded` flips to `true`, `Escape` closes it, and tapping a link closes it and scrolls to the right section.
12. Every CTA links to `/register` and the header link points to `/login` (both 404 for now — expected until the auth step).
13. Clicking each header nav anchor scrolls to its section with the heading fully visible below the sticky header.
14. Tab order flows header → hero CTAs → sections → footer, with a visible focus ring on every interactive element; FAQ items open and close with `Enter` / `Space`.
15. Applying the `.dark` class to `<html>` in devtools renders a correct dark theme with readable contrast throughout.
16. `.env.example` exists, documents `DB_URI` and `NEXT_PUBLIC_SITE_URL` with placeholder values, and contains no real secrets.
17. `git status` shows changes only in the files listed under "Files to change" and "Files to create".
